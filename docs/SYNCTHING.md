# Sync, offline work and recovery

Open myDrive's tray popup and choose **Sync**. On Windows and macOS, myDrive checks the existing Syncthing configuration and authenticates its local API. A running engine is reused. If it stopped when SyncTrayzor or Syncthing.app closed, myDrive starts the installed engine directly without a browser or GUI wrapper. The engine continues after myDrive exits. Background refresh retries if it stops later. **Connection settings** lets you choose a different config.xml or a manual loopback API address and key. Manual endpoints bypass automatic startup/installation and use only that connection. Keys are kept in Windows Credential Manager or macOS Keychain.

## Background engine

The shared `engine.ensure` action serializes setup using an OS file lock. An occupied API address with invalid authentication/TLS is an error, not a reason to launch a competing instance. Syncthing's native config/database lock also protects against a racing GUI wrapper. Missing or invalid explicitly selected configurations are never replaced. Default database paths reported by the installed engine are reused; a custom config selection assumes a combined config/database directory. Custom split directories require configuring the engine outside this UI.

Discovery checks SyncTrayzor, common Windows installer paths, WinGet/Scoop and PATH; on Mac it checks Syncthing.app in system/user Applications, Homebrew and PATH. Only if none exists, myDrive installs pinned official Syncthing v2.1.7 for Windows x64 or Mac Intel/Apple Silicon in its per-user `engine` directory. No administrator access or system-wide installer is needed. HTTPS downloads must match source-pinned SHA-256 hashes. The system archive tool streams only the known executable member into an atomic new file; existing binaries are never overwritten. This is an engine-only install. First setup requires internet; normal offline work does not.

Startup output is saved in `syncthing-engine.log` beside app preferences. No new OS login service is registered; enable myDrive's normal login startup for unattended startup. See [official CLI options](https://docs.syncthing.net/users/syncthing.html), [the pinned release](https://github.com/syncthing/syncthing/releases/tag/v2.1.7) and [Mac bundle layout](https://github.com/syncthing/syncthing-macos#settings).

Windows starts the background engine with `CREATE_NO_WINDOW` and `--no-console`, including its monitor/worker. It does not combine `CREATE_NO_WINDOW` with `DETACHED_PROCESS`, which would cause Windows to ignore the no-window flag. The engine still outlives the requesting core process, with no request-pipe handles inherited. Mac launches directly through the process API with closed standard streams; Terminal is not involved.

## Folder and file controls

To stop an entire folder, use its **… → Stop syncing folder…** menu and confirm. This removes only the local folder configuration. Existing files and archived versions stay on disk, other devices keep their folder configurations and copies, and unrelated folders keep syncing. A redacted configuration backup is saved in the app's syncthing-backups directory before removal; encryption passwords are omitted. If the folder changed since it was displayed, myDrive refuses the stale stop request. Add the folder again to resume sharing. Use Pause for a temporary stop that keeps the folder in the sync list.

In the popup, use **+ → Sync a folder…**. Choose a folder and device, then **Start syncing**. **This project** selects the myDrive project directory. A connected device is selected first by default. Accept a new folder offer once on the other computer if required. Local sharing does not let myDrive silently choose a remote path. Existing shares retain their configuration.

New shares skip generated build/SDK/cache directories by default. The option is in the share form. Existing folders retain their ignore rules. A subfolder can have its own share with different devices. For example, share GitHub between Mac and laptop, then GitHub/project between Mac and desktop. Open the parent folder's file browser, enter the subfolder and choose **Sync this subfolder with another device…**, or select it using **+ → Sync a folder…**. Only the selected folder is offered; parent membership, file selections and ignore rules stay unchanged. The destination accepts the child as its own folder and chooses its local path. Existing parent ignore rules do not automatically become the child's rules.

myDrive refuses to share overlapping roots with a common remote device, including when adding a device to an existing share. This prevents a direct duplicate sync route. Paused shares still count, and existing folder members are retained. Syncthing itself [warns that nested folders have caveats and circular shares must be avoided](https://docs.syncthing.net/users/faq.html#am-i-able-to-nest-shared-folders-in-syncthing). myDrive checks the current computer's configuration; it cannot prove the absence of a loop created manually across other computers. Keep the receiving child root separate from other synced roots on the destination. Stopping a child share keeps its files; its contents continue syncing through the parent to the parent's devices.

**Choose files** shows files on disk and files announced by peers. **Sync** and **Stop** take effect immediately. Stop excludes future changes on this computer and keeps existing copies, including copies on other devices. These selections apply to every peer of this local Syncthing folder; they are not a separate selection per destination device. A more specific managed file selection takes precedence over a managed containing folder. Concurrent external rule edits are rejected and must be reloaded.

Files present locally open in their usual applications and work offline. A remote file that is not present locally can be prioritized for download, but a device holding it must reconnect before it can open. Syncthing watches saved files, checks blocks, uses temporary transfers, and resumes when devices reconnect. Files that have never arrived are not available offline.

Ordinary saves propagate automatically. If both devices independently save different content to the same file, Syncthing selects a current copy and preserves an alternative edit. myDrive groups these under **Saved alternative edits**, with a button to open each copy. The underlying alternative files remain available in Explorer and propagate to peers. The app does not claim to merge arbitrary Photoshop, Blender, Office, database or other binary files. Live collaborative editing needs support from the editing application or an application-aware collaboration service. SMB offers live access to one network copy; locking behavior depends on the editor and server and does not provide automatic two-way offline replication.

New folders preserve alternative edits without an automatic count limit and keep the last 20 received versions. Existing folders are not changed automatically. **Protect version history** enables the same history if none exists, preserves any custom history policy, and enables unlimited alternative retention. Versioning is configured separately on each computer. Syncthing archives received replacements/deletions, not every local editor save.

Use a folder's **… → Saved versions** to restore received history. Restoring is an intentional edit that will sync to other devices. myDrive first saves the current file in LocalApplicationData/myDrive/syncthing-restore-backups, then restores through Syncthing and scans the path. The saved backup path is returned by the core; configuration/rule changes have separate backups in syncthing-backups. An editor changing a file during preparation can cause restoration to stop rather than overwrite that edit.

The test script uses two fresh loopback-only daemons and fresh directories. It covers sharing, real file transfer, file exclusion/resume, offline divergent edits, preservation on both devices, received history and restore. Production Syncthing folders are never used as fixtures.

References: [Syncthing synchronization](https://docs.syncthing.net/users/syncing.html), [received versioning](https://docs.syncthing.net/users/versioning.html), [ignore rules](https://docs.syncthing.net/users/ignoring.html), [REST API](https://docs.syncthing.net/dev/rest.html).

## Local browser data and sync locks (2026-11-16)

Short message: **Local browser data is locked.**
Fix: **Keep the app's browser data outside the synced folder.** Project source can keep syncing while the app stays open.

OSEAN STUDIO APPS had 32 `hashing: open ... file is being used by another process` errors, all in `TV LIVESTREAM/Project Files/data/windows-profile/EBWebView/` (cookies, browser cache and lock files). These were local browser databases, not source-code conflicts. OSEAN TV Windows 1.2.1 stores its WebView profile and extracted runtime DLLs in `%LOCALAPPDATA%/OseanStudio/OSEAN TV/`. On first launch it copies existing login/settings data without overwriting an existing local profile; the original is retained. A locked migration stops safely and can be retried after closing other app copies.

Only the exact old TV `windows-profile`, `windows-profile-verification` and `windows-runtime` directories were excluded in this local Syncthing folder. All earlier ignore rules were preserved and backed up. Source code, app assets and ordinary project files remain selected. An open application is not itself a sync error: exclude machine-local state, not the whole project. A sharing error on an ordinary document still requires identifying that document's owning app; this browser-data fix must not be applied blindly to it.

Verification: eight migration checks and the actual Windows shell verification passed. With the updated TV dashboard open, its WebView process uses the LocalAppData profile, and Syncthing reported idle, zero pull errors, zero folder errors and zero pending files. macOS runtime testing remains deferred.

## Storage cleanup (2026-11-16)

The synced apps folder was about 60.17 GB across 192,752 files. Large portable Python/AI runtimes, downloaded models, Rust/Tauri compilation caches, SDKs and local media had accumulated beside source. Rebuildable build/download caches were deleted. Models, installed engines, user media, outputs and useful archives were preserved outside the sync tree under `C:\myDriveData`.

Local NTFS junctions keep old paths working without a second copy. Exact ignore rules exclude these junctions, the local myDrive Windows installation, and old nested version history from transfer. Windows-only compatibility links are not a portable configuration; other platforms use their own native data directories. Do not delete `C:\myDriveData` to remove the links: that directory holds the preserved actual files. Broad `**/bin` rules were replaced with explicit generated-output paths so Rust `src/bin` entry points remain selected for sync.

Build scripts now direct toolchains and compilation output outside the project; the Wallpaper dev build also omits large debug symbols/incremental output. AI apps show storage use/location and allow model removal without choosing a replacement. Shared dependencies and project media are preserved.

Final verified result: about **193 MB / 966 files selected for sync**, with the folder resumed and idle, zero pull/folder errors, and no pending local files. Physical project files total about **422 MB / 1,846 files**, including local app binaries excluded from transfer. The MacBook was offline at verification; peer transfer waits for reconnection. Roughly **25.72 GB of generated build/download files were deleted**. Actual models/media/runtime data is preserved in the external data directory.
