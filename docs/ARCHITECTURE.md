# Architecture

`Core/` is Rust, without AppKit, WinUI or GTK imports. A small JSON request/response protocol on standard input/output is the first native bridge. Each request runs in a worker process, so blocking protocol APIs never run on the UI thread and cancellation can terminate the worker. This boundary can later become an async library API without changing native UI models.

The core owns bookmark validation/persistence and a common `FileClient` interface (`list`, `download`, `upload`, `mkdir`, `delete`, `rename`). `LocalClient` covers local folders and native SMB filesystem paths; SFTP, WebDAV and S3 implement the same interface. The current API is file-oriented, not a complete random-access filesystem API.

The Windows shell owns native credentials and passes secrets only through the child process's redirected stdin. Passwords are not command line arguments or bookmark fields. The bridge returns structured results and does not print credentials. OS credential APIs remain native platform adapters; future macOS and Linux shells must implement Keychain and Secret Service adapters.

The tray popup and full window share one Window, state and operation handlers. Compact rendering lives in `Windows/App/QuickPopup.cs`: a small native header, status summary and dense rows. The NavigationView pane and idle footer are hidden in compact mode; setup/details use native menus and dialogs. Expanded mode retains the sidebar and roomier screens. Switching preserves the active connection, path, listing and operation. File pickers and modal editors suppress automatic dismissal; closing dialogs restores the small size. Closing either view keeps the tray service running; Quit terminates it. [Native UI requirements](NATIVE-UI.md) apply to every platform shell.

Bookmark updates use a temporary file in the same directory, flush it, then replace atomically. An unreadable/corrupt existing file is an error and is not silently reset. Windows editor saves use credential rollback if bookmark persistence fails. A current-user mutex and named pipe activate the existing UI on subsequent launches. External bookmark writers still require coordination.

`Core/src/syncthing.rs` connects to Syncthing over authenticated loopback HTTP(S), with bounded requests and optional local certificate trust. The shared engine owner reuses a running instance or starts a checksum-verified official binary from myDrive's cache with the existing configuration and identity. An OS file lock serializes setup. The native shells hold the owner open through a private pipe, and closing it stops engines started by that owner. Standalone Syncthing processes and manually configured endpoints retain their own lifecycle. Credentials travel through private pipes, and dashboard results omit secrets. The `syncthing.events` action provides bounded long-poll updates.

The macOS shell (`Mac/App/Sources/`) is AppKit/SwiftUI: an `NSStatusItem` with a 344 pt popover capped at 420 pt, an optional full window, and the same sidecar boundary as Windows (one `mydrive-core` process per request, secrets only via stdin, cancellation kills the process). macOS specifics: a Keychain generic-password adapter (service `myDrive`, account `myDrive/<bookmark-id>`); SMB volumes are discovered from `getmntinfo` and served by the core's local client, so mounting stays a native shell duty — health probes are deadline-bounded stats and remounts go through the system mounter so Finder's Keychain credentials apply; config discovery probes `~/Library/Application Support/Syncthing/config.xml` first. Attention cards classify folder error text (`Attention.swift`) and pair it with fixes. Fixes that belong on a peer travel as whitelisted JSON envelopes in the shared folder's `.mydrive-requests/` directory: Syncthing delivers them, a peer myDrive shows Accept/Decline, executes the fix only if the kind is on the safe list, and writes a response that syncs back. Both ends refuse non-whitelisted kinds.

New roots are registered paused; generated-cache exclusions are installed before unpausing. Only the local and selected devices are added to a new share. Exact existing roots retain membership and custom settings; nested roots are allowed only when all remote memberships are disjoint from every overlapping root; same-peer overlap is rejected before mutation. New device records explicitly carry an empty encryption password for ordinary trusted sharing. Encrypted/untrusted device setup remains in Syncthing. Existing ignore content is preserved alongside a marked managed block, compared again before mutation, and backed up first. This is best-effort stale-update detection because the Syncthing API has no atomic compare-and-swap for ignore files.

Syncthing owns its database, transport, reconnect, checksum validation and file reconciliation. myDrive exposes saved alternatives instead of claiming automatic binary merging. New roots enable simple received versioning and preserve conflict copies. Restore backs up the current file outside the shared root, avoids same-second archive collisions, invokes the official restore endpoint, then scans the restored path. Versioning covers incoming replacements/deletes and is configured per computer; it is not a backup of every local save.

Native Windows SMB calls live in `Windows/Network/smb.rs` and execute inside the cancellable sidecar. The UI can enforce a deadline even when a Windows network provider blocks. A mapped drive already in use is accepted only when its actual remote path matches.

Downloads use a temporary file and commit only on success without replacing an existing destination. Uploads create a new destination and refuse overwrite. Local uploads commit a temporary file without clobbering the destination. SFTP uses exclusive create; cancellation can leave a partial remote file. WebDAV uses `If-None-Match: *`; S3 uses conditional PutObject. Providers must actually honor these conditions; real-provider validation is required.

Path validation rejects traversal, NUL, backslashes and colon in relative API paths. Local filesystem operations resolve existing symlinks before checking containment. Filesystem TOCTOU races and remote server symlink behavior require further hardening before exposing untrusted multi-user roots.

The C++ Cloud Files spike is deliberately separate from the product. It proves the local API can register, connect, create a dataless file, hydrate it and unregister. It does not supply remote hydration or uploads, and is never launched automatically by the product.
